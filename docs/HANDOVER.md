# AsterHive（星巢）项目交接与架构全景文档

> **文档定位**：本文件记录 AsterHive（星巢）项目的全景架构、核心设计约定、关键避坑指南与当前开发进度，用于迁移至后续 AI Agent 或接手开发者无缝续做。
> **本轮更新**：执行验收工作流修复与用户开发指导思想。
> **验证范围**：本地回归与隔离执行验证，不等同于生产跨设备完整任务验收；以当前发布记录为准。
> **生产约束**：本次部署保持自动派发、独立审核和工蜂暂停；服务器更新不会自动升级已安装的工蜂。

## 开发本项目的指导思想

1、防过度防御:几乎不会发生的边界/并发问题，讲清概率并经用户确认后再加，严禁为“理论上更稳”私自膨胀代码。
2、入口单次校验:外部数据只在边界校验一次，内部靠类型系统流转，禁止层层重复判断。
3、拒绝提前抽象:单次使用的逻辑就近内联，不随意提前拆分无意义的helper。
4、控制复杂度:非必要不用try/catch，能单函数清晰搞定的别硬拆


## 一、项目定位与核心实体

AsterHive 是一个专为可信局域网/分布式物理设备设计的 **多设备分布式 AI 协作平台**。它以**任务看板**与**实时聊天室**为协作中枢，将人类用户、服务端决策主脑、独立审核员以及分散在多台物理设备上的工蜂 Agent 组织成有机协作的蜂群（Bee Fleet）。

### 核心角色定义

1. **用户（User）**：在系统内拥有绝对最高权限，匿名请求直接视为该唯一的“老板”；
2. **蜂后（Queen / Orchestrator）**：常驻服务器的决策核心，基于内置 Pi 运行时拉起。负责顶层需求拆解、建卡、预指派，并在聊天室与用户交流；
3. **独立代码审核员（Reviewer）**：具备**独立于蜂后的模型组配置**（例如蜂后采用推理模型，审核员采用大上下文严格代码模型）。在工蜂提交任务后，对任务分支进行自动双盲审查，合格后自动合并至服务器主仓；
4. **工蜂（Worker Bee）**：分布在各物理设备（Windows / Linux / macOS）上的动手执行者，按看板自动巡检领活，在隔离工作区完成开发与自测，上交证据并回传代码包。

## 二、代码库代码组织（Monorepo 结构）

项目采用 npm workspace 维护，目录结构清晰：

- **`apps/server/`**：服务端核心
  - `src/http.ts`：RESTful 路由、静态文件托管、`/scripts/` 脚本分发与 SSE 实时总线；
  - `src/repo-manager.ts`：服务器托管 Git 仓库（Bare Repo）管理器，实现快照导出、结果导入与任务合并；
  - `src/brain.ts`：蜂后（Queen）与独立 Reviewer 的执行调度管线；
  - `src/orchestrator-tools.ts`：蜂后与 Reviewer 可调用的受限结构化工具面；
  - `src/verbs.ts`：工蜂交接协议动词实现（`claim`, `checkpoint`, `submit`, `release`, `next`）；
  - `src/scheduler.ts`：Nomad 风格的资源感知多维调度匹配器；
  - `src/fleet-radar.ts`：全蜂群算力池聚合与停滞任务预警雷达；
  - `src/evidence.ts`：小文件入 SQLite BLOB、大文件落磁盘的分层证据存储；
  - `src/pi-runtime.ts`：蜂后扩展（extensions）与技能（skills）的热管理。
- **`apps/web/`**：原生前端（Vite + TypeScript）
  - 遵循 Zinc 暗色体系 + 蜂蜜金唯一品牌色规范，零重型第三方 UI 框架依赖，极致秒开；
  - 视图模块：`views/board.ts`（看板）、`views/room.ts`（聊天室）、`views/fleet.ts`（舰队雷达）、`views/agents.ts`（接入中心）、`views/settings.ts`（设置中心）。
- **`apps/worker-zcode/`**：工蜂执行内核与适配器
  - `src/main.ts`：工蜂守护进程主循环（自愈注册、多板轮询、任务领取、心跳保活）；
  - `src/pi-executor.ts`：基于 `@earendil-works/pi-coding-agent` 的进程内执行内核；
  - `src/workspace.ts`：临时快照工作区构建、代码提交与结果 bundle 回传；
  - `src/sdk.ts`：相对路径桥接，解决 Node 24 类型剥离对 node_modules 的硬性报错。
- **`packages/sdk/`**：工蜂薄 SDK 与独立 CLI 工具
  - `src/index.ts`：工蜂标准协议客户端与硬件能力采样器；
  - `src/cli.ts`：单文件免装 CLI 工具（可直接用于终端操作与代码本地导入）。
- **`scripts/`**：部署与安装自动化脚本
  - `install-hive.sh`：服务器端 Docker 容器交互式一键部署脚本；
  - `install-bee.ps1` / `install-bee.sh`：Windows 原生 / Linux 托管工蜂一键安装与自愈升级脚本；
  - `uninstall-bee.ps1` / `uninstall-bee.sh`：工蜂一键停止、远端注销、文件销毁与 PATH 恢复脚本；
  - `worker.tar.gz`：仅 53KB 的工蜂源码精简包，由服务端直接内网秒级分发。

## 三、关键架构设计与核心技术机制

### 1. 托管工蜂（Managed Worker Bee）架构

为实现“在全新裸机设备上一行命令接入”，工蜂彻底摒弃了对宿主机预装外部 Agent（如 OMP / ZCode Desktop）的依赖：
- **进程内隔离会话**：直接在守护进程内调用 `@earendil-works/pi-coding-agent` SDK 启动一次性 `inMemory` 内存会话；每张卡跑完即弃，绝不发生跨任务的上下文泄露；
- **专属 Hive 纪律**：注入 `WORKER_SYSTEM_PROMPT`，强制约束工蜂仅在临时工作区相对路径内工作、禁止访问宿主敏感凭据、改动基于任务分支 commit 留痕；
- **自适应常驻降级机制（Windows）**：
  - 优先尝试系统计划任务；
  - 若在普通用户（非管理员）权限下遇到“拒绝访问”，**自动秒级降级为当前用户的自启动项（`%APPDATA%\...\Startup\AsterHive-worker.vbs`）并无黑框隐藏拉起后台进程**，达成 100% 零管理员提权要求；
- **依赖全自动自举**：
  - Node 缺失/低于 23.6 → 自动下载并部署官方便携版 Node 24；
  - Git 缺失 → 自动下载并部署官方 MinGit 2.48.1 便携版（~28MB）；
  - 启动器 `start-worker.cmd` 顶部显式锁定环境 PATH，确保后台常驻服务 100% 拥有 Node 与 Git 执行环境。

### 2. 服务器主仓托管模式（Managed Repo Mode）

这是 AsterHive 相比传统分布式 Worker 最关键的飞跃：**代码的唯一事实源保存在服务器持久卷 `/data/repos/<boardId>.git` 中**。
- **工作区生命周期**：
  1. 领活：工蜂从服务器端拉取基于主仓 HEAD 生成的短期任务快照 `snapshot.bundle`；
  2. 解包：工蜂在系统临时目录下解包并在任务分支 `asterhive/<taskId>` 动手开发自测；
  3. 回传：任务完成后，外层管线（`workspace.ts`）自动检测分支新 commit，生成 `result.bundle` 上传至服务端；
  4. 审查：服务端接收 bundle 并登记到主仓的 `refs/asterhive/tasks/<taskId>`，触发独立 Reviewer；
  5. 合并：审查通过后，服务端执行原子 fast-forward/merge，工蜂本地临时工作区即刻销毁。
- **重点避坑点**：
  在 `workspace.ts` 中，必须同时支持“模型在会话内自行调用 `git commit`”与“模型未 commit 留给外层统一 commit”两种行为。必须通过比对分支当前 HEAD 与下发时的 `baseCommit`，只要产生有效提交，就必须打包回传 bundle，杜绝工作树干净被误判为“无变更”而丢失任务分支的问题。

### 3. 双模型与独立代码审核员（Reviewer）

- **双盲机制**：审核员与蜂后解耦，在 Web 设置页中拥有独立模型组配置与启停开关；
- **自动化管线**：
  - 提交进入 `Review` 泳道时，系统自动提取任务分支相对于默认分支的真实 Diff；
  - 独立审核员评估修改范围是否符合验收标准、是否存在安全隐患；
  - 审核通过（`pass`）→ 自动集成合并至默认分支，流转至 `Done` 并发聊天室通报；
  - 审核未通过（`reject`）→ 自动打回 `InProgress` 并附带结构化修正要求（允许最多 2 次重做）；
  - 连续 3 次未过 → 自动挂起（`blocked`）并提示用户人工介入。

### 4. 内网信任与零令牌哲学

- **单用户极简**：局域网内浏览器请求被视为唯一的系统拥有者（用户角色），无需输入密码或 Bearer Token；
- **Token 归属化**：Token 仅用于物理设备/工蜂的身份归属与防伪鉴权；
- **凭据最小化**：工蜂的模型 API Key 仅保存在本地设备文件（`~/.asterhive/worker.json`，权限 0600），服务器不经手、不中转；
- **热升级身份继承机制**：
  - 安装脚本更新时，会自动探活本地既有凭据；
  - 若在当前 Hive 仍有效，强制保留原 Handle 与 Token，杜绝重装产生 `-2`、`-3` 冗余工蜂；
  - 若已在服务器注销（返回 401），则自动触发自愈重注册。

### 5. 项目代码库初始化规则与引导机制（Managed Repo Onboarding）

为彻底解决新建看板后“蜂后不理解初始化”及用户不知如何将代码导入服务器的问题，系统建立了完整的自动化检测、工具链与引导闭环：
- **概念与目的**：
  - “初始化项目代码库”是指为看板在 AsterHive 服务器建立持久化托管 Bare 主仓（`/data/repos/<boardId>.git`）；
  - 这是后续所有跨设备工蜂拉取任务快照 bundle、在临时分支开发自测并由独立 Reviewer 自动合并的前提。
- **触发时机**：
  1. 新建看板（`board.created`）且代码库处于 `empty` 状态时；
  2. 看板仓库配置更新（`board.updated` 变更了 `repo` 或 `repoSource`）时；
  3. 用户在聊天室主动提及“初始化项目”、“拉取代码”或“导入仓库”时。
- **蜂后能力与工具链**：
  - **`asterhive_board_repo_status(boardId)`**：蜂后随时查询看板主仓状态（`repoMode`, `repoStatus`: empty/queued/running/ready/failed, `head`, `source`），并给出 `needsInit` 诊断；
  - **`asterhive_board_repo_init(boardId, mode, url)`**：
    - `mode: 'clone'`：服务端直接发起从远程 Git 地址拉取并建立主仓；
    - `mode: 'local_import'`：为用户生成精确的源设备 CLI 导入命令（`node packages/sdk/src/cli.ts repo import --board <boardId> --path <本机目录> --url <hiveUrl>`）；
    - `mode: 'empty'`：建立初始空仓库。
  - **蜂后纪律九（系统提示词规范）**：未初始化前绝不盲目建代码卡；主动在聊天室 @用户 并提供“A: 远程克隆 / B: 本机目录导入 / C: 空项目 / D: 暂不初始化”四个选项，并按用户意图调用工具执行。
- **Web 界面状态横幅**：
  - 看板页面顶部检测到 `managed` 模式且 `repoStatus === 'empty'` 时，自动渲染醒目的黄色引导横幅，并提供“复制导入命令”快捷按钮。

## 五、环境信息与常用运维命令

### 1. 生产服务端部署（基于当前 server-199 实例）

- **访问地址**：`http://192.168.1.199:8067`
- **代码目录**：`~/AsterHive`
- **数据卷持久路径**：`/data`（容器内），包含 `asterhive.db`、`repos/`（托管仓库）、`evidence/`（大证据文件）；
- **换版部署流程**（在本地开发机执行）：
  ```bash
  # 1. 确保测试全绿并完成 git commit
  npm test
  # 2. 远端清理旧源码（保留 .env）并解压最新 git archive
  ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes rover@192.168.1.199 "find ~/AsterHive -mindepth 1 -maxdepth 1 ! -name '.env' -exec rm -rf {} +"
  git archive HEAD | ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes rover@192.168.1.199 "tar -x -C ~/AsterHive"
  # 3. 远端重建镜像并重启容器
  ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes rover@192.168.1.199 "cd ~/AsterHive && docker compose up -d --build"
  ```

### 2. 工蜂安装与运维命令（直接在目标设备执行）

- **Windows 目标设备（PowerShell，零管理员权限要求）**：
  ```powershell
  # 安装或热升级工蜂（地址自动注入，自动自举 Node 与 MinGit）
  irm http://192.168.1.199:8067/scripts/install-bee.ps1 | iex

  # 完全卸载销毁工蜂（向服务端注销、终止进程、删除文件并恢复 PATH）
  irm http://192.168.1.199:8067/scripts/uninstall-bee.ps1 | iex
  ```
- **Linux / macOS 目标设备（Bash）**：
  ```bash
  # 安装或热升级工蜂
  curl -fsSL http://192.168.1.199:8067/scripts/install-bee.sh | bash

  # 完全卸载销毁工蜂
  curl -fsSL http://192.168.1.199:8067/scripts/uninstall-bee.sh | bash
  ```
