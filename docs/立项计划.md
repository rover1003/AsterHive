# AsterHive（星巢）· 通用多 Agent 任务分派系统 · 立项计划

> 项目定名：**AsterHive（星巢）**——蜂群隐喻与系统一一对应：蜂后＝主脑（只协调、从不外出觅食，正合"只分派不执行"）、工蜂＝worker、蜂巢＝看板+聊天室、摇摆舞＝@ 调度通讯；仓库名 `asterhive`（2026-10-24 用户选定）。
> 状态：立项定稿（v1）· 起草日期 2026-10-24 · 起草人 ZCode（用户口述，多轮对话收敛）· 2026-10-24 用户确认开工
> 存放说明：本文档起草于 AsterHub-reference 项目（原暂存 `项目现状/`），2026-10-24 随独立立项整体迁入本仓库 `docs/`，作为种子设计文档；开发工作在本仓库进行。

## 1. 定位

一句话：**AsterHive（星巢）——部署在服务器上的通用多 agent 任务分派系统**——一块持久化共享看板 + 一个只做拆解、分派、验收的主脑 + 一个主脑与全体 worker 同处的聊天室控制面 + 可插拔的各路执行 agent。

四个根本属性：

- **通用**：不绑定 AsterHub 或任何单一项目。任何能在某台机器上运行、又能发 HTTP 请求的对话式 agent（CLI 产品、SDK 程序、脚本作业）都可以注册为 worker；被管理的项目只需能被 worker 访问（检出/克隆）。
- **独立**：独立仓库、独立部署（服务器容器），与任何被管理的项目仓库零代码耦合。
- **主脑专职**：主脑只做目标拆解、任务分派、证据验收、向用户汇报，**绝不亲自执行任务**。主脑可由外部 agent 兼任，也可用项目内置的极简 agent 运行时；两者都只挂载看板 API 作为工具，"不执行"是结构性约束而非 prompt 自觉。
- **用户只说自然语言**：沿用现有交接铁律。用户在聊天室里说话即可分派、干预、验收；不运行命令、不写台账。

非目标（明确排除）：

- 不做实时 CI / 线上监控（沿用"快照不是监控"的边界；本系统管理的是任务流转，不是被管项目的运行时观测）。
- 不做全自动无人值守的拆解+执行链（Hermes 实测教训：一次性结构化拆解远优于全自动规划执行）。
- 不做公网多租户 SaaS；目标是局域网 / 单团队自治部署。

## 2. 三个面：聊天室、看板、台账

系统对外的呈现是两个视图，底层是一份日志：

| 面 | 给谁看 | 内容 |
|---|---|---|
| 聊天室 Room | 用户（主入口）+ 主脑 + worker | 一条时间流的对话：分派、上交、进度、干预、汇报 |
| 看板 Board | 用户（结构化总览）+ 主脑 | 卡片、泳道、依赖图、占用、证据 |
| 台账 Events | 服务器内部（+审计页） | 追加式事件日志；聊天室与看板都是它的投影 |

关键设计：**聊天室和看板不是两套数据**。所有动作（用户发言、主脑分派、worker checkpoint、提交、状态迁移）都先落为事件；聊天室按时间流渲染，看板按任务聚合渲染，同一条事件两边都可见。事件只追加、不物理删除，修正以新事件表达。

## 3. 血统：从三个来源各取什么

### 3.1 Hermes Kanban（NousResearch/hermes-agent）

取：

- 任务五字段模型：task / lane / assignee / depends_on / 时间戳。
- 泳道即工作流：Backlog → Ready → InProgress → Review → Done，配 WIP 限制（默认每泳道 2–3）。
- `next` 动态拉取：未认领 + 已解锁 + 按优先级取第一条。
- `kanban_db` 写纪律：写前快照备份（保留 3 份）、结构化写、写后验证、验证失败自动回滚、独立写审计日志。
- dashboard / backup / restore 的产品形态。

教训（照单全收）：

- **一次性建路线图，优于全自动规划执行**（其全自动代码模式实测 9 任务 4 失败 3 超时；改用一次性结构化路线图后全部通过）。
- **显式 `next` 优于自动指派**；大小模型混编可行（Plan 用小模型、Execute 用大模型）。
- 泳道不是装饰——共享板本身就是对 agent 的行为训练场（执行 agent 被拉进 Review 处理过一次卡死后，此后自觉守泳道）。

不取：assignee 自标 Done（与信任分层冲突，见 §5.2）。

### 3.2 本项目交接协议（项目现状/交接协议.md）

取（全部平移为服务器语义）：

- claim / checkpoint / release 动词与事件流推导占用。
- TTL 断线判定（认领后超时无活动即视为断线，他人可接管；默认 240 分钟可调）。
- 认领文件清单互斥（两份活跃认领的文件清单不允许重叠，服务器拒绝）。
- **信任分层**：worker 自报告不可信；Review → Done 只能由主脑/用户核实证据后移动。
- 任务卡带验收标准（acceptance）与证据登记（evidence）。
- 用户永远不运行命令、不写台账，协议由 agent 自动执行。

### 3.3 DSH 上游（packages/，只作参考与一种运行时，不构成依赖）

- `SubagentProvider` 合同（packages/subagent/subagent/src/types.ts:344）：provider 注册 + 能力广告模式，作为 worker adapter 的设计参考。
- `subagent-acp` / `subprocess-ssh`：拉起外部 CLI（ACP 协议或任意 argv，本地/SSH 远端）的现成思路。
- `asterhub-automation`：定时/事件唤醒一个 agent 会话自主执行的模式（其"应用关闭即停、并发 2、超时 30 分钟"的进程内上限，正是本系统把调度放进服务器的理由）。
- `webhook-github`：HMAC 签名 + credential-ref 的 HTTP ingress 安全模板。
- continuables 的 inbox 注入（packages/subagent/subagent/src/continuation.ts:82）：运行中 agent 接收外部消息的模型，聊天室干预落地 worker 的参考。
- SDK（stdio JSON-RPC，仅 initialize / session.prompt / shutdown 三个方法）：外部程序驱动 DSH 的既有通道。

边界事实：DSH 没有通用 HTTP ingress（唯一 HTTP 入口是 GitHub 签名专用 webhook）；jobs / todo / deliverables 均为单会话私有，无跨 agent 共享状态；调度上限在进程内。这些缺口即本系统存在的理由。

## 4. 总体架构

```
用户（自然语言；聊天室内发言即最高优先级指令）
   │ Web UI（聊天室为主入口，看板/注册表/审计页并列）
   ▼
┌──────────────────────────────────────────────────────┐
│ 分派服务器（独立项目，部署于内网服务器，容器部署）              │
│                                                        │
│  聊天室 · 看板 · 审计页         SQLite(WAL) · 追加式事件日志   │
│  HTTP API（token 鉴权）· SSE 事件流 · 写前快照备份            │
│  内置主脑运行时（模式 B，可选组件，UI 配置模型）                │
└──────────────────────────────────────────────────────┘
   │ Worker 协议（HTTP + token）
   ├── 主脑 A（外部 agent 兼任，如用户的 ZCode 会话，走同一套 API）
   ├── push 型 worker：服务器/主脑经启动器按需拉起的 headless 运行
   │     （zcode -p / omp / ACP CLI / Nomad 作业 / 任意脚本）
   └── pull 型 worker：常驻进程轮询 /next 自取任务
```

三角色职责与禁令：

| 角色 | 职责 | 禁令 |
|---|---|---|
| 服务器 | 状态、规则、鉴权、审计、备份、事件流、看板与聊天室渲染 | 不跑任何模型推理；不理解自然语言 |
| 主脑 | 拆解目标建卡与依赖、分派或放行、验收证据、移动 Review→Done、向用户汇报 | 不执行任务；不直接写代码/文件 |
| worker | 认领、执行、checkpoint、上交证据 | 不自行把自己的卡移到 Done |

Web 界面构成：聊天室（默认视图）· 看板 · **Agent 总览页（fleet 视图）** · Agent 接入页（注册、命名、token、启动器配置、启停）· 主脑设置页（模型与运行参数，见 §8）· 审计页。所有设置在界面完成，用户不需要编辑配置文件。

Agent 总览页采用 Nomad Jobs/Nodes 页的风格：一屏纵览全体 agent 的实时工作状态，SSE 驱动刷新。每个 agent 一行/一卡：

- 状态色标：绿＝工作中 · 灰＝空闲 · 黄＝TTL 内无心跳（断线候选）· 红＝上报阻塞或失败 · 置灰＝停用。
- 当前占用：任务号 + 标题（**工作的目标摘要**）+ 认领起算的已进行时长。
- 最新进度：最近一条 checkpoint 摘要（一行）。
- 心跳新鲜度与累计完成数（可选）。

顶部聚合条：在岗 / 空闲 / 断线计数、各泳道 WIP 占用。点击 agent 进入详情页：任务历史、checkpoint 流、证据链接、事件时间线。push 型一次性运行同样注册为 agent，终态后移入历史。该视图是既有事件的纯投影（claim→占用、checkpoint→进度、heartbeat→在线），agent 无需为此额外上报任何数据。

## 5. 核心数据模型

### 5.1 Task（任务卡）

Hermes 五字段 + 交接协议字段 + 通用化新增：

| 字段 | 说明 | 来源 |
|---|---|---|
| id | 短号（T42 / BUG-17 / AUX-3，沿用现有编号习惯） | 协议 |
| title / detail | 短标题 + 详细说明 | Hermes + 协议 |
| lane | Backlog / Ready / InProgress / Review / Done | Hermes |
| assignee | agent id 或 unassigned | Hermes |
| depends_on | 任务 id 列表；上游进 Done 自动解锁并记 autoUnblockedAt | Hermes |
| priority / category | P0–P2 / 类别 | 协议 |
| acceptance | 验收标准，主脑验收时逐条对照 | 协议 |
| workspace | 工作区描述（仓库/路径/目标机器）——通用系统必需 | 新增 |
| files | 预期触碰文件清单，用于认领互斥校验 | 协议 |
| evidence | 证据登记（路径 + 机器 + 说明） | 协议 |
| protectedPaths | 本任务禁触路径 | 协议 |
| createdAt / updatedAt / autoUnblockedAt | 时间戳 | Hermes |

### 5.2 泳道与信任边界

- worker 可写区间：claim 即 InProgress，submit 即 Review。**Review → Done 仅主脑/用户可操作**，API 按角色拒绝——信任分层（自报告不可信）的落点。
- Ready = 已拆解且依赖已解锁、可领；Backlog = 路线图占位 / 未拆解。
- WIP 限制：每泳道/每 agent 可配，默认 2–3。

### 5.3 Agent（注册表）

id、显示名与 @ 句柄（全局唯一，聊天室 @ 调度用）、类型（主脑 / worker / 人）、能力声明、token、心跳与 TTL、当前占用、接入方式（pull token / push 启动器配置，界面可改）。

### 5.4 Message（聊天室消息）

author（user / orchestrator / worker / system）、kind（dispatch / submit / progress / intervention / question / report / system）、mentions（@ 句柄列表，服务器据此机械投递）、taskRef（可空，绑定任务卡）、content、时间戳。

### 5.5 Event（追加式台账）

一切状态迁移与消息都是事件；只追加，不物理删除。

## 6. 聊天室：统一控制面（用户主入口）

- **同室原则**：主脑、每个活跃 worker、系统（状态变更播报）、用户同处一个房间（建议每 board 一房 + 全局摘要频道，最终粒度见 §13）。用户打开界面即可一目了然：谁被派了什么、谁交了什么、卡在哪里。
- **消息流形态**：
  - 分派：主脑 → worker（任务号 + 摘要 + 验收标准）。
  - 上交：worker → 主脑（结果 + 证据登记）→ 主脑验收 → 系统播报泳道变更。
  - 进度：worker checkpoint 摘要进房间（可折叠/可静音）。
  - 干预：用户 → @某 worker / @主脑 / 全体；**最高优先级**，可暂停、改派、回答问题、直接验收。
  - 汇报：主脑定期或事件触发向用户发全局摘要。
- **命名与 @ 调度**：每个 agent 有唯一 @ 句柄（界面注册/命名时设定；`@主脑` 为保留句柄，指向当前主脑，模式 A/B 通用）。主脑与用户用 `@+名称` 定向调度，例如：
  - 派活：「@zcode，请领取 T42 任务，任务详情在 <链接/路径>」
  - 上交：「@主脑，D3 任务已完成，结论在 xxxx/xxxx 文档中」
  - **路由是机械的**：服务器只解析 `@句柄` 词元并投递（维持"服务器不理解自然语言"的架构约束），语义理解发生在被 @ 的 agent 那里——zcode 收到后自行调用 claim，主脑收到上交后自行验收落账。消息中的任务号（Txx 等）由服务器机械识别并挂 taskRef，点击跳卡片。
  - **结构化与对话式双通道**：主脑的"分派"工具一次调用同时完成任务指派与房间 @ 消息；worker 的 submit 事件在聊天室渲染为一条 @主脑 的上交消息（同一事件，两个投影）。没有 API 集成的对话式 agent 也可纯靠 @ 发言参与，由主脑代为落账。
  - 无 @ 的消息为广播；用户的无 @ 发言默认唤醒主脑（用户说话即指令）。
- **干预如何到达 worker**：
  - pull 型 / 空闲 worker：下次 `next` 或 `checkpoint` 的**响应体携带待达消息**——checkpoint 是双向同步点。
  - 运行中的交互式 agent（ZCode / OMP 会话）：worker 侧适配器把房间消息注入会话（参考 DSH continuables 的 inbox 模型）。
  - 运行中的内置主脑（模式 B，Pi）：Pi 原生支持运行中注入 steering 消息，用户干预可直接送达。
  - headless push 运行：中途注入是已知限制；主脑可选择中断重启（干预消息并入重启 prompt）或等待终态。
- **与看板联动**：消息带 taskRef，点击跳转卡片；卡片页内嵌该任务的消息子流。
- **多表面（远期）**：Web 界面是聊天室的第一表面；三期接入飞书群作为第二表面，消息双向桥接、@ 调度语义不变（见 §12）。

## 7. HTTP API 草案（v0）

鉴权：每 agent 一个 bearer token，可吊销；用户走 Web 会话。所有写操作入审计；写前自动快照（保留最近 3 份）；结构校验失败拒绝写入。

| 组 | 端点 | 说明 |
|---|---|---|
| 看板 | GET /boards；POST/PATCH /boards/:b/tasks；POST /tasks/:id/depends | 多 board：每项目/工作流一板 |
| 领取 | POST /boards/:b/next | 未认领 + 已解锁 + 按优先级；原子认领 |
| worker 动词 | POST /tasks/:id/claim、/checkpoint、/release、/submit | 对应交接协议动词；checkpoint 响应携带待达干预消息 |
| 聊天室 | GET/POST /boards/:b/messages | 发言与拉取；服务器机械解析 @ 句柄并投递；用户干预即 POST |
| 事件 | GET /events（SSE） | 主脑唤醒与 UI 实时刷新共用 |
| 总览 | GET /overview | fleet 视图数据源：每 agent 状态、当前任务与目标摘要、最新 checkpoint、心跳新鲜度；纯聚合端点，不要求 agent 新增上报 |
| Agent 接入 | POST /agents/register；PATCH /agents/:id；POST /agents/:id/heartbeat | 注册、命名、启停、接入方式（pull token / push 启动器）均在界面管理；心跳刷新 TTL |
| 主脑设置 | GET/PUT /settings/orchestrator | provider / baseURL / model / apiKey（加密存储）及各项运行参数（唤醒策略、WIP、拆解/汇报开关等），界面管理，模式 B |
| 审计 | GET /audit | 台账与写审计查询 |

## 8. 主脑设计

### 8.1 双模式

- **模式 A（外部 agent 兼任）**：用户的 ZCode / OMP 会话直接以完整 API 操作服务器。适合有人值守、主会话额度充足时；API 就绪即可用，零额外开发。
- **模式 B（内置极简运行时）**：项目内置一个只装"看板 API 工具"的极简 agent，**在项目界面中配置它自己的高水平模型（例如 GPT-6）**，常态无人值守运行。运行时候选：

| 候选 | 优势 | 代价 |
|---|---|---|
| Pi（pi.dev · earendil-works/pi，MIT；极简 TS agent harness；官方 TypeScript SDK 嵌入模式，另有 print/JSON 与 RPC 驱动；扩展/技能模型，15+ provider 统一接入，树状会话历史，运行中可注入 steering 消息） | 极简、TS 同栈；嵌入是官方一等模式；steering 原生支持用户干预直达运行中的主脑 | 常驻无人值守需一层薄守护壳（用其 SDK/RPC 驱动）；立项首周做一次嵌入 PoC |
| DSH headless profile（经 SDK / ACP 启动） | 会话持久化、插件生态、subagent 能力齐备 | 重：拖整个运行时；版本耦合；调度上限仍在进程内 |
| 自研薄壳（OpenAI 兼容 API + 工具循环，数百行） | 完全可控、零外部依赖 | 轮子自己造；仅在前两者都不合适时兜底 |

- 推荐路径：一期用模式 A 跑通闭环；二期内置主脑首选 Pi（2026-10-24 已核实：MIT 许可证；官方 TypeScript SDK 嵌入模式；OpenAI 在其 15+ provider 之列，配置 GPT-6 级模型无障碍；用户确认所指即 pi.dev）。

### 8.2 工具面（结构性保证"只分派不执行"）

主脑可用的工具 = 服务器 API 本身：建卡、建依赖、分派、放行 next、读证据、发房间消息、向用户提问。**不提供 shell、文件、浏览器等任何执行类工具**。

### 8.3 触发与纪律

- 唤醒事件：用户新消息、有卡进 Review、worker 上报阻塞、新任务创建、定时摘要。
- 拆解纪律：一次性建完整路线图（Hermes 教训），建完即停，不顺着执行链自跑。
- 验收循环：读证据 → 对照 acceptance → Done 或退回（附退回理由，任务回 InProgress 并通知 assignee）。
- 模型配置：主脑的模型在 UI 独立配置（provider/baseURL/key/model，如 GPT-6）；worker 各自用什么模型由其所有者决定，服务器不感知。

## 9. Worker 接入

### 9.1 最小 Worker 协议

任何 runtime 只要能发 HTTP 就能当 worker，共 5 个调用：register（一次性，声明 id/能力/启动方式）、next/claim（取活）、checkpoint（进度与断点，响应收干预消息）、submit（结果 + 证据 + 下一步建议）、release/heartbeat（释放/续命）。

提供一个薄 SDK（TS 先行，Python 随后）把协议包成库；各 agent 适配器只写三件事：怎么启动它、怎么把任务塞进它的 prompt、怎么把它的输出变成 submit。

### 9.2 启动器（Runner，服务器侧可插拔）

本地 exec（同机拉起任意 CLI）、SSH（远端任意 argv）、Nomad job（重型/批量计算，沿用既有集群）、Docker、ACP spawn（Claude Code、Codex、Gemini CLI 等 ACP 协议 CLI）。

### 9.3 首批 worker（建议）

ZCode headless、OMP、DSH headless profile、ACP 系 CLI、Nomad 脚本作业。

### 9.4 工作区管理：git 仓库为唯一事实源（2026-10-24 用户问定）

星巢服务器只管任务流转，**不托管被管项目的代码**。以"开发 A 项目"为例，目录这样放：

- **A 项目是一个 git 仓库**（GitHub 私有仓库为主流形态；如需内网权威副本，可在 199 加 bare mirror 或 Gitea，后置可选）。
- **每台 worker 设备各自克隆一份本地副本**，路径按各设备习惯（如 `C:\开发目录\A` / `~/dev/A`）。不共享网络盘——网络文件系统不适合 agent 高频读写，且公网设备根本挂不了内网盘。
- 跨设备协作由服务器既有机制保证，无需新增共享存储：
  1. 任务卡 `workspace` 字段写明 repo + 分支/ref（+ 目标机器），主脑派活时给出；
  2. `files` 认领互斥：两台设备的活跃认领文件清单不允许重叠，服务器直接拒绝——从根上防止两台机器同时改同一处；
  3. 上交以**分支/提交**为证据（evidence 登记分支、commit、路径），主脑对照 acceptance 验收；合并回主干是验收后的动作。
- 非 git 工作物（文档、数据、截图）以"路径 + 机器"登记进 evidence，二期上传端点后可入库。

## 10. 安全、部署与运维

- **部署**：内网服务器 **Docker 容器**（docker compose 管理，例如 8067 端口；2026-10-24 用户已定）。局域网内其他设备（乃至公网设备）统一以 worker 身份经 HTTP + token 主动接入；外部设备经既有 **WireGuard** 隧道接入局域网（DDNS + 动态公网 IP 已就绪），对服务器而言全部设备皆为内网，token 由隧道加密保护；仅三期飞书回调等真公网入站才需反向代理 + TLS。
- **鉴权**：agent token + 用户 Web 会话；token 可吊销；操作全量入审计。
- **备份**：写前快照 ×3 + 定期全量备份（沿用 Hermes backup 形态）。
- **存储**：SQLite WAL 起步（服务器是唯一写者，单进程串行化所有写）；schema 保持可平移 PostgreSQL（部署环境已有实例，可复用）。
- **证据文件**：一期"路径 + 机器"登记；二期上传端点（小文件入库，大文件登记校验和）。
- **密钥**：各 worker 的模型 API key 由 worker 侧自持；服务器只加密保存主脑的模型配置。
- **技术栈建议**：TypeScript + Node（与 DSH / ZCode 生态同栈）、Fastify 或 Hono、better-sqlite3（WAL）、Web UI 用 Vite + 原生 TS（沿用项目现状看板的零依赖渲染思路）。均为建议，立项时可换。

## 11. 与当前项目的关系与独立立项

- **独立仓库**：新开仓库 `asterhive`（托管位置见 §13），本文档整体迁出作为种子（design doc + roadmap 起点）。本仓库不引入任何相关代码，不触发其门禁。
- **AsterHub 协作迁移（可选、后置）**：系统可用后，项目现状/ 的协作可整体迁为一块 board。映射：status-data.js → board 数据；handoff.mjs 的 claim/checkpoint/release → 同名 API；journal/*.jsonl → 事件日志；问题提交记录.jsonl → intake 消息；check 校验（文件互斥 / TTL / 认领后无 checkpoint）→ 服务器内置校验。迁移完成前 项目现状/ 协议照旧运行，两不干扰。
- **DSH 侧集成（三期，可选）**：如需 DSH 内深度集成（worker 唤醒插件、把整块板注册成 SubagentProvider 等），按既定分层在 asterhub-* 插件层实现，不改 DSH 核心。

## 12. 分期路线

**一期（MVP：先跑通端到端闭环）**

- 服务器：HTTP API（看板 + worker 动词 + 消息 + SSE）+ SQLite + 审计 + 备份。
- Web UI：聊天室（默认视图，含 @ 调度）+ 看板 + Agent 总览页（fleet 视图）+ Agent 接入页（命名/token/启动器配置）+ 主脑设置页。
- 主脑：模式 A（用户的 ZCode 会话人工充当）。
- Worker 接入：设备侧主动注册、pull 型拉取优先（ZCode headless 先行）；push 启动器（Nomad / SSH）后置可选（2026-10-24 用户定向：一切外部设备统一以 worker 身份接入）。
- 验收标准：在聊天室里完成一次真实小任务全流程——用户提目标 → 主脑建卡并以 @worker 派活 → worker 执行并 @主脑 上交 → 主脑验收 Done；用户全程只发自然语言，主脑与 agent 接入均在界面配置。

**二期（无人值守主脑 + 拉取型 worker）**

- 内置主脑（Pi 运行时 + UI 模型配置，如 GPT-6）+ 事件唤醒。
- pull 型 worker + 心跳 TTL 断线接管。
- 证据上传、干预消息注入运行中会话。
- 验收标准：用户离开 24 小时，一个多任务多依赖的目标被自动拆解、分派、执行、验收（人工抽查证据确认）。

**三期（生态与规模化）**

- DSH 插件层集成、TodoWrite 式同步、多 board 完善、PostgreSQL、ACP push 启动器、通知渠道（邮件摘要等，参考 Hermes Schedule 集成）。
- 飞书接入（用户远期计划）：以飞书群作为聊天室的第二表面——入站用飞书事件订阅 + 验签（复用 §3.3 webhook-github 的验签/受信规则模式）把群消息转成房间消息，飞书 @mention 双向映射 agent @ 句柄，用户在群里 @ 分派 / @ 干预与 Web 端完全等价；出站把 dispatch / submit / 泳道变更播报经群机器人推回群，任务卡与证据链接以飞书卡片渲染。Web 聊天室与飞书群是同一事件日志的两个投影，互为镜像。
