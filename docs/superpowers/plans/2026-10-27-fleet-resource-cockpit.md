# AsterHive 跨设备执行管理、资源大屏与项目导入开发计划

> 状态：功能开发与端到端验收已完成（分支 `fix/fleet-release-readiness`，基线 `68c4ff2`），等待用户授权合并推送与生产部署。本文档记录该计划的完整设计与实际落地情况。

**目标**：建立可追踪的跨设备 Agent 执行管理，让蜂后根据任务要求、节点能力与负载定向派发可并行且不冲突的任务，让用户看清任务实例的真实活动与结果，并提供信息丰富、视觉精致的硬件资源大屏。

**架构**：任务卡描述业务目标，执行实例记录一次指定工蜂的执行；蜂后负责规划与决策，服务端运行时负责可靠分派、事件、状态与恢复，工蜂负责执行并报告可观察事件。工蜂采样经认证心跳上报，服务端以快照及有界历史通过 SSE 更新任务视图和大屏；保活、执行活动、真实进展与最终验收分开。沿用 HTTP + SSE，不把它称为工蜂双向长连接；仅在验证表明延迟或网络代价不满足指标时另行评估 WebSocket。

**技术栈**：TypeScript、Node.js `node:os`、Hono、SQLite、现有 SSE 总线、Vite/原生 TypeScript、现有工蜂 SDK；不引入 Nomad、Redis 或外部遥测服务作为运行依赖。

## 1. 需求与边界

1. 面向任意用户设备，不将 199 测试环境中的机器数、机型、核心数、地址或配置硬编码进产品。支持 Windows、Linux、macOS；不支持或未上报的指标明确为“未知”。
2. 大屏借鉴 Nomad 的信息完整性，不复制其外观；沿用 `docs/DESIGN.md` 的 zinc 中性色、蜂蜜金和语义色令牌，优先清晰的层级、布局和可读性。
3. 用户要求蜂后综合任务难度、机器能力、可用模型和实时负载指定工蜂；工蜂不能抢未指派任务。蜂后不可用或无符合条件节点时，任务保持 Ready 并说明原因，不能假装已派发或放宽硬约束。
4. 可并行的互不冲突任务应能同时执行；文件所有权、依赖、WIP、仓库集成及审核必须协同，不能用更高并发牺牲正确性。
5. `minMemoryGb` 维持“总物理内存最低值”既有语义。实时空闲内存是负载信号，不等于内存预留；CPU 空闲率不等于可预留 CPU。明确要求动态 CPU 限额但遥测未知/过期时，不得声称满足。
6. 工作区已有未提交实现必须保留；计划实施时先进行代码审查与补测，不得重写已有成果。无授权不部署、不推送、不删除生产数据、不向真实用户发送消息。
7. 设备遥测只采集资源信息；不采集进程命令行、密钥、剪贴板或用户个人内容。任务必要的文件范围仅在用户授权的项目任务上下文处理，不作为设备遥测采集。可选 GPU、磁盘等只在跨平台有真实数据时展示，不支持时显示未知，不编造。
8. 蜂后应能在当前看板权限内直接只读项目资料，并亲自负责规划和拆解；不以工蜂替代规划决策。只读能力须禁止跨看板、路径逃逸、敏感文件与凭据访问；不因此开放仓库写入或任意命令。
9. 任务卡与执行实例不是同一个对象：一次重试、改派或重做必须有独立执行 ID 和历史。工蜂在线、模型/工具活动、里程碑报告、用户等待与验收证据各自记录，不能相互冒充。
10. 新建项目选择本地目录导入后，用户仍可在看板中查看实际看板 ID、创建时填写的 Git 地址和准确导入指引，刷新后不丢失；明确区分“用户填写的地址”与“已克隆/导入的仓库来源”，避免误报状态。

## 3. 目标数据与接口契约

### 3.1 工蜂采样

保持现有 `DeviceTelemetry` 的可空字段：`cpuPercent`、`memoryUsedGb`、`memoryTotalGb`、`memoryFreeGb`、`memoryPercent`、`loadAvg`、`uptimeSec`、`taskInProgress`；增加/调整字段须先同步 SDK、服务端、前端类型和版本兼容说明。CPU 根据同一设备连续两次系统 CPU tick 差值计算；首帧或采集失败为 `null`。内存 GB 使用 GiB（1024³ 字节），界面标明单位。Windows 不显示无意义的固定零 load average。

- 建议默认 10 秒一次，沿用现有节流；可在验证后配置，但不能因为一次网络慢请求阻塞工蜂任务执行。
- 心跳 `POST /agents/:id/heartbeat` 使用工蜂凭据并仅允许对应设备上报；旧版心跳无 telemetry 时仍能更新存活，不伪造遥测值。服务端记录接收时间，客户端时间若保留仅作参考。
- 明确 `taskInProgress: null` 是工蜂声明空闲、缺字段是未知；服务器任务状态与设备自报不一致时展示双方状态，调度以服务端任务记录为准。

### 3.2 快照、历史与推送

- `GET /api/fleet/telemetry`：全体节点、静态规格、最新帧、带采样时间的近期历史及汇总；`GET /api/fleet/telemetry/:id`：单节点详情。保留现有 `/events` 的 `agent.telemetry` 事件；新增字段/改名先更新 `apps/web/src/api.ts`。
- 默认历史 60 秒、每节点最多 60 帧；60 秒未收到更新显示过期。缓存上限和清理策略必须可解释，节点数超过当前 200 上限时不得静默丢失在线节点；给出明确上限/错误或按活跃节点安全淘汰。
- 重启/升级导致内存历史丢失时显示“历史重新积累”，不补零。长周期持久化历史、跨实例共享和历史分析不在本次范围；若后续需要，单独明确存储、保留期和权限。
- SSE 只推送受限指标。为每连接设置有限队列并合并同节点最新帧；慢消费者丢弃可重建的中间遥测并通过快照恢复，不能无界增长。断线后自动重连并重新获取快照，阻止旧事件覆盖新快照。
- 汇总必须区分“总设备”和“实际新鲜上报设备”；CPU 平均值注明统计口径和样本数，未知值不计为 0。已用/可用内存汇总只覆盖有有效数据的在线样本。

## 4. 调度设计

### 4.1 蜂后决策与候选评估

1. 蜂后拆解任务时写明目标、验收、依赖、预期写入路径、可确认的 OS/架构/CPU/内存/执行器/模型要求；任务难度由蜂后结合上下文判断，不能仅凭 CPU 瞬时负载推断。
2. `matchTaskToWorkers(ctx, taskId)` 第一阶段按节点启用/在线、看板参与者、任务显式硬条件筛选；第二阶段按新鲜资源、工作状态、模型匹配及可证实的历史记录排序，并返回分数与逐条理由。无数据标记未知，不按空闲节点加分。
3. 蜂后通过 `asterhive_match_task` 查看候选，再用 `asterhive_dispatch` 指定具体工蜂。Ready 新建、依赖解锁及工蜂恢复上线时需要可重试唤醒或周期性扫描，避免单次事件丢失导致任务永久无人派发。蜂后离线、模型失败或无候选时保持 Ready，可见说明并允许用户重试。
4. 评分仅建议，不把分数当作资源预留。服务端定向派发和认领时再次在同一事务检查任务仍为 Ready、目标工蜂身份/参与资格、硬性要求仍满足、依赖已完成、WIP 有容量以及文件互斥；并发过时的建议须明确返回冲突，让蜂后重新评估。任何人工覆盖硬条件的产品能力不在本次范围。

### 4.2 并行安全与容量

- 将 `nextTask` 与 `claimTask` 收敛到同一校验及原子写入流程；拒绝未指派任务、他人任务和重复领取。蜂后只指定对象，工蜂通过现有轮询查询自身待执行任务并 claim；轮询不是抢公共池。
- 定义文件声明契约：任务 `files` 为仓库相对写路径；同一仓库的相同路径及目录/后代路径互斥。拒绝绝对路径、`..` 和逃逸；明确 Windows 分隔符、大小写及符号链接处理。无法事先声明写范围的代码任务按同仓库保守串行或由蜂后先完成范围分析，不能将空清单视作安全并行。只读任务用已有 `reads` 和 `workspace.noCode` 明确标识，不把 noCode 当成自动通过。
- 文件冲突与 WIP 判定必须与实际领取状态写入在同一数据库事务中；并发提交 Review 时 WIP 检查也须在同事务中完成，防止并发穿透。默认 3 是现有配置，不自动按在线数改写用户配置；提供可见容量与排队原因，是否调整由用户决定。
- 保持独立 Reviewer 的失败不自动通过；不同任务的开发可并行，当前 Reviewer 串行是明确瓶颈。先测量 Review 排队时间，再设计有界审核并发；同仓库最终集成应有仓库级串行保护与冲突处理。任务取消不得引发审核后的迟到合并或撤销已经合并的代码。

### 4.3 Harness 执行实例与事件

1. 任务是目标与验收条件；执行实例（`attempt`）是一张任务卡在指定工蜂、工作区与基线上的一次执行。记录唯一执行 ID、任务 ID、工蜂 ID、序号、仓库基线、执行器、创建/确认/开始/结束时间与结果；历史不可被新一轮覆盖。具体数据库表与 HTTP/SDK 字段由实施任务先冻结并做迁移测试，旧任务不得丢失。
2. 蜂后给运行时提交明确任务目标、验收、依赖、文件所有权、工具权限与目标工蜂；运行时持久化派发并由指定工蜂确认。轮询只是可靠传输机制，不允许未指派的节点抢执行。主控能够按执行 ID 查看结果、向当前执行发送干预，并按授权请求取消；不依赖聊天消息充当唯一状态。
3. 执行状态至少区分：待接收、已接收、执行中、等待模型、等待工具、等待用户、执行完成待验收、失败、取消中/已取消、失联结果未知；“疑似停滞”是依据多久未观测到活动生成的提示，不自动等同失败或卡死。业务泳道 Ready/InProgress/Review/Done 与执行状态分开投影。
4. 结构化事件与保活分开：工蜂心跳仅证明连接；模型请求/工具开始与结束由运行时在可观察时上报；里程碑为工蜂明确报告；完成时记录结果、证据与错误。事件关联执行 ID、单调序号或幂等键、服务端接收时间，补传必须去重且不倒退状态；不得上传密钥、私人内容、完整命令行或未授权文件内容。无法观测的阶段显示未知，不虚构工具或模型活动。
5. 进度卡同时展示最近心跳、最近可观察活动及时间、最近明确里程碑、当前等待对象/耗时；超过阈值提示“暂未看到新活动”，不保证执行已停。旧工蜂的固定“任务持续执行”checkpoint 只作为保活，不得刷新真实进度或压制停滞提醒；兼容历史记录，不修改历史事实。
6. 网络断开、超时、服务重启或发送中断时，执行状态为结果未知，保留工作区及文件所有权。禁止自动重发写操作、重复执行、自动释放任务或将旧结果合并。恢复先核实设备/执行句柄及已发生的副作用；只有确认旧执行已停止，或采用隔离工作区并通过执行代次/栅栏阻止旧结果和迟到提交后，才能重新派发。取消/重启等有副作用的动作须符合用户授权及审计要求。
7. 子 Agent 的“完成”只是声明。运行时先接收结果与提交、测试证据；蜂后或独立 Reviewer 对照验收后才更新业务终态。执行完成、工蜂结果、Review 通过和仓库合并是独立状态，失败、取消和缺证据不得自动通过。

### 4.3.1 当前 Pi 会话的只读观察

- 目标：用户在任务详情中订阅当前执行实例的 Pi 会话，看到已授权展示的实时会话内容、流式回复、工具调用及其开始/结束/失败状态；不通过截屏、tmux 或模拟终端获取。会话观察不等于任务已完成、审核通过或工蜂进程健康。
- 当前代码事实：`apps/worker-zcode/src/pi-executor.ts` 已对单次内存 Pi 会话调用 `session.subscribe()`，但当前上报侧只发送部分活动摘要，不提供完整会话镜像；会话管理器是内存模式，工蜂重启后不能假定历史存在。OMP RPC/CLI 和其他执行器的事件能力需分别验证，未支持时显示“此执行器暂不支持会话观察”，不得展示伪造内容。
- 参考 [Pi Web UI](https://github.com/kkkiio/pi-web-ui) 在 Pi 进程内订阅事件并向页面转发的方式，但不直接部署其无内置认证的监听服务；采用现有工蜂主动出站到 Hive、Hive 向页面推送的模式，不要求客户设备开放入站端口。优先沿用认证 HTTP 上报与 SSE；是否需要双向连接仅在实际验证后另行决策。
- 会话事件须绑定看板、任务、执行实例/轮次、指定工蜂、事件序号和服务端接收时间。事件包含用户已授权查看的会话消息、助手可见文本增量、工具名及调用 ID、工具状态与可安全展示的结果摘要；将增量按消息/内容块正确重组，工具事件按调用 ID 关联。执行器未暴露的模型内部思考不可推断或伪造；供应商实际返回的推理内容涉及隐私和策略，默认不采集、不展示，除非后续明确授权并实现单独控制。
- 默认只读，页面不提供终端、任意命令、输入注入或控制 Pi 会话的能力；如需干预，沿用现有经授权通道，不把观察连接变成隐蔽控制入口。不得将完整工具参数、命令行、文件内容、凭据、私人数据或其他未经授权内容默认上传；按白名单构造事件，在工蜂侧经跨分片安全过滤后再发送，服务端再次校验并安全转义。无法确保安全的片段直接隐藏并标明原因，不承诺启发式脱敏能识别所有秘密。
- 浏览器首开时获取当前执行实例的受限快照，再按序消费实时事件；事件与快照按同一序号衔接，去重、防乱序及过期实例栅栏校验。连接断开显示断线和最后接收时间；重连通过游标补取可用事件，无法补全时明确标记缺口，不把缺口绘制成完整历史。传输与缓存有界，慢客户端可断开并重新拉取快照；服务重启、工蜂进程结束或历史过期后若不能恢复，明确显示不可恢复而非编造内容。
- 仅允许经认证、拥有当前看板访问权限的用户查看；工蜂只能上报自身获派且当前轮次有效的事件，禁止跨看板、跨任务读取或伪造。为事件内容设置明确的容量、保留期限、清理规则和审计；执行历史与实时片段分开，旧轮次事件不能覆盖新轮次。会话采集产生新的数据暴露面，实施前须冻结可见字段、存储及保留期，并以沙箱测试凭据泄露、跨事件切分和越权访问。


### 4.4 与 Nomad 的关系
